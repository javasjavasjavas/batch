Qué encontré

La portada pública entregaba 845 bytes de HTML con el título genérico “Batch: Bulk Image Processing UI”. El contenido dependía de ejecutar JavaScript. No había descripción, canonical, sitemap ni robots.txt propios. Steam y los diez kits de plataformas tenían dos URLs para el mismo contenido. Las preguntas frecuentes solo insertaban sus respuestas después de abrirlas.

El problema principal era que tener distintas pantallas no se traducía en páginas bien identificadas y accesibles desde el HTML inicial. La implementación corrige esa base antes de ampliar la cantidad de contenido.

Cambios aplicados

  • HTML generado para cada URL: portada, directorio, 15 herramientas, ayuda, 6 guías y páginas institucionales. Se utilizan los mismos componentes que ve el visitante.
  • Títulos, descripciones y encabezados: específicos por página. El contenido se alinea con funciones existentes y límites reales.
  • Una URL preferida: canonical a https://batchimagekit.com; redirecciones 301 de once alias /app/plataforma hacia su herramienta pública.
  • Sitemap y robots: generados en cada build. El sitemap contiene solo las 27 URLs públicas preferidas.
  • Control de indexación: veinte rutas del editor, revisión, procesamiento y resultados usan noindex,follow. Permanecen rastreables para que el buscador pueda leer esa indicación. Las URLs inexistentes disponen de un archivo 404 propio.
  • Datos estructurados: WebSite, Organization, WebPage, BreadcrumbList, WebApplication, TechArticle e ItemList según corresponda. Sin valoraciones inventadas ni promesas de resultados enriquecidos.
  • Contenido de herramientas: tablas de tamaños tomadas de los presets reales, pasos de preparación, límites, referencias y enlaces a herramientas relacionadas. Los presets prácticos se distinguen de la orientación oficial.
  • Preguntas frecuentes: respuestas presentes en el HTML mediante desplegables nativos. Se corrigió el texto sobre GIF animados para coincidir con la aplicación.
  • Enlaces internos: los accesos de navegación apuntan a las herramientas públicas y las guías enlazan a las funciones relevantes.
  • Rendimiento: editores y pasos de trabajo cargados bajo demanda; caché larga para archivos con hash. Las imágenes de muestra ya no quedan invisibles esperando a JavaScript.
  • Presentación al compartir: metadatos Open Graph y Twitter, imagen de 1200 × 630 y favicon propio.
  • Prevención de regresiones: el build audita metadatos únicos, un H1 y canonical por página, enlaces, archivos, schema, sitemap, exclusiones y redirecciones.

Guías nuevas

  • Cómo redimensionar fotos de productos sin recortar: diferencia entre límite de tamaño y marco exacto, padding y elección del formato.
  • Cómo reducir el peso para subir imágenes: dimensiones, calidad, PNG y comprobación de límites reales.
  • Cómo elegir entre WebP, PNG y JPG: transparencia, compatibilidad y lo que una conversión no recupera.

Los textos del sitio se mantienen en inglés, como el producto actual. No se generaron traducciones automáticas ni páginas casi idénticas para cada variante de palabra clave.

Estado de publicación

Publicado y verificado en batchimagekit.com el 21/10/2026. Cloudflare completó la publicación automática del commit SEO 39da1fd. La auditoría del sitio público pasó: 27 páginas con canonical e indexación correctos, 20 rutas internas con noindex, 11 alias 301, respuesta 404 real, robots.txt y sitemap.

Con la autorización del usuario se activó la regla Batch Image Kit canonical domains, asociada a la lista batchimagekit_canonical_hosts. Contiene dos redirecciones permanentes 301: www.batchimagekit.com y batchimagekit.pages.dev hacia https://batchimagekit.com. Se verificaron respuestas reales conservando rutas y parámetros. La opción de incluir subdominios está desactivada para no redirigir los hosts de vistas previas.

Lo que queda fuera del código

  1. Search Console y Bing Webmaster Tools: verificar propiedad, enviar el sitemap y revisar indexación. No se accedió a esas cuentas; no hay todavía evidencia de rankings o tráfico atribuible a estos cambios.
  2. Medición: observar impresiones, clics, CTR y páginas de entrada en Search Console. Si se instrumentan conversiones, medir inicio y finalización del proceso sin enviar imágenes, nombres de archivo ni datos privados.
  3. Rendimiento real: medir Core Web Vitals en campo cuando exista tráfico y optimizar las páginas que fallen. La carga principal aún incluye React, navegación y componentes comunes.
  4. Actualización de requisitos: los tamaños se apoyan en el catálogo del proyecto, revisado el 20/10/2026. No se revalidó individualmente cada regla de todas las plataformas en esta auditoría SEO.

Prioridad para crecer

Primero: comprobar indexación y búsquedas reales de Steam, kits para tiendas y capturas de apps. Son necesidades específicas que el producto resuelve con un flujo completo; priorizarlas es una hipótesis de ajuste al producto, no una estimación de competencia.

Después: mejorar páginas con impresiones y pocos clics, y ampliar guías con ejemplos propios para preguntas que ya aparezcan en Search Console. Si una variante como “WebP to JPG” demuestra demanda, darle una página propia solo cuando tenga instrucciones diferenciadas y el convertidor preconfigurado para esa tarea.

Distribución: conseguir menciones legítimas en comunidades de desarrolladores, creadores y vendedores con demostraciones útiles. No se enviaron mensajes ni se compraron enlaces. Considerar español u otros idiomas cuando la demanda justifique traducciones completas y su mantenimiento.

Alcance del resultado: se mejora la capacidad de rastreo, la claridad de las páginas y la experiencia de entrada. La indexación, las posiciones y el aumento de tráfico dependen del buscador, la demanda, la competencia y las señales que se acumulen; no se pueden garantizar ni medir inmediatamente con este cambio.
